<objective>
Fix the 10 failing `create*ResourceIT` integration tests in `portfolioService` using Option A (client-supplies-ID), per the user's explicit choice over server-side ID generation and consistent with PROJECT.md's locked decision that UUID PKs are manually assigned, not DB-generated.

**Deviation from the literal task instruction — read before executing Task 2:**
The originating task description said to *remove* the `if (dto.getId() != null) throw ...` guard from all 10 controllers entirely. Verification during planning found this would silently flip 10 *currently-passing* tests (`create*WithExistingId`, one per entity, present in every one of the 10 `*ResourceIT.java` files) from pass to fail. Those tests POST a DTO whose id was already persisted and assert `status().isBadRequest()`. If the guard is deleted outright, `xxxService.save(dto)` routes through `JpaRepository.save()`; since the DTO now always carries a non-null id (that's the whole point of Option A), Spring Data JPA's default `isNew()` check treats the entity as "not new" and calls `entityManager.merge()` instead of `persist()` — merge() finds the existing row by id and just performs a silent UPDATE, returning success instead of 400. Net effect of literally deleting the guard: the originally-failing 10 tests would start passing, but 10 *different*, currently-passing tests would start failing — `mvn verify` would NOT reach 0 failures.

Task 2 therefore replaces the guard's condition (`dto.getId() != null`) with an existence check (`repository.existsById(dto.getId())`) instead of deleting the guard. This is the minimal, in-scope fix that satisfies Option A (a valid create always carries a client id) while preserving the exact behavior the `create*WithExistingId` tests already verify (you cannot create a new row with an id that's already taken). It touches only the same 10 controller files already in scope, adds no new dependencies (every controller already has its own `xxxRepository` injected), and does not touch the DTOs' `@NotNull` annotations.

**Also flagged, not fixed (out of scope for this plan):** all 10 domain entities (`Asset.java`, `AssetRatio.java`, `Broker.java`, `BrokerAccount.java`, `IncomeEvent.java`, `Operation.java`, `Position.java`, `Rebate.java`, `TaxEvent.java`, `Valuation.java`) carry `@Id @GeneratedValue` on their `id` field — this contradicts the "manually assigned, not DB-generated" architecture decision in PROJECT.md. It is currently harmless under this fix (repository-routed saves always carry a non-null id post-fix, so Spring Data JPA uses `merge()`, which bypasses the generator), but it is architecturally vestigial JHipster scaffold and worth a deliberate cleanup decision later. Do not remove `@GeneratedValue` as part of this plan — flag it in the SUMMARY instead. Also do not touch the known thread-unsafe SSE emitter `HashMap` in `KafkaConsumer.java` or any other item in `.planning/codebase/CONCERNS.md` — out of scope.
